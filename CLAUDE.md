# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

KVACK (Knowledge, Verification & Automation Compliance Kit, formerly "QA Copilot"; code identifiers such as the `qacopilot` package, `QACOPILOT_` settings, database and container names keep the old name so nothing breaks): a GenAI document assistant for the Gressingham quality team (ingest PDFs, extract certificate fields, RAG Q&A with citations, approval-gated agent actions). The plan, phases and design rationale are in `PLAN.md`; this file covers only what is built. Phase 1 is done (provider, health endpoint, spike). Phase 2 is built apart from an LLM classifier fallback: PDF extraction + OCR, rules classifier, per-type chunking, local embeddings, Qdrant hybrid store, cross-encoder reranking, `/ingest`, streaming `/ask` with citations, and the golden-set eval runner. Phase 3 is built (compared against the toolkit's `calibration/extract.py`, see `evals/TOOLKIT_COMPARISON.md`): extraction schemas + LLM extraction, Postgres storage (Alembic), `/certificates`, and the deterministic CoA-vs-spec checker. Phase 4 is built: a LangGraph agent with a mandatory human approval, a Mailer interface (file + Outlook), per-user API keys, an append-only audit log, and `/feedback` tied to Langfuse traces. Phase 5 is built: a React + TypeScript front end in `web/` (chat with streaming and citation links, document upload, approval queue). Phase 6 is built apart from screenshots: golden set v2 (35 questions, 27 synthetic documents incl. adversarial cases), end-to-end answer evals, LLM-judged faithfulness, an offline CI gate over recorded results, a self-hosted live-eval workflow, per-release scores in Langfuse, and the README.

It started inside a larger internal repo but is independent of the Flask toolkit it was compared against: its own venv (`qa-copilot/.venv`), its own `pyproject.toml` files, no imports from `gressingham_automation`. It can be developed from the Windows work PC or the Linux laptop (see below); this file is meant to stand alone, so it works with a sparse checkout containing only `qa-copilot/`. Real company documents never go in git (`data/real/` and `evals/spike_docs/` are gitignored); `data/samples/` is synthetic only.

## Developing on the Linux laptop

The laptop (Linux, 32 GB RAM, no GPU) can run everything except the Windows-only pieces.

```bash
git clone https://github.com/Nuud1es/KVACK.git
cd KVACK

# one-off: Postgres + Qdrant + Langfuse on this machine (see infra/)
./infra/setup-laptop.sh --install-docker        # skip the flag if Docker is already installed

python3 -m venv .venv && source .venv/bin/activate   # needs: sudo apt install python3-venv
pip install -e "packages/qacopilot[dev,tracing]" -e "services/api[dev]"
cp .env.example .env
```

`.env` on the laptop:
- Services are local: `QACOPILOT_DATABASE_URL=postgresql+psycopg://qacopilot:<password>@localhost:5432/qacopilot` (password in `infra/.env`), `QACOPILOT_QDRANT_URL=http://localhost:6333`, `QACOPILOT_LANGFUSE_HOST=http://localhost:3000` with the keys from `infra/.langfuse/secrets.env`.
- LLM: `QACOPILOT_LLM_BASE_URL`, `_LLM_API_KEY` and `_LLM_MODEL` point at the LLM server. A `*.ts.net` host is only reachable over **Tailscale** (the laptop must be logged in: `sudo tailscale up`). The LLM is reached at a public HTTPS name such as `https://llm.example.com/v1`, which needs a real API key in `.env` (`curl` without one answers 401, which is how to tell it is up) and no Tailscale.** A server on a private network needs only a placeholder key because the SDK refuses an empty one. Never put keys in git or in chat. **If the API runs on a machine that is not on the tailnet (the Windows work PC cannot install Tailscale: no admin), the LLM host must be exposed with Tailscale Funnel and MUST have `--api-key`; `infra/check-llm.sh` warns when the server answers a keyless request (HTTP 400/422 instead of 401/403).**
- If the work LLM is unreachable, run a small MoE model locally on CPU (e.g. gpt-oss-20b via `llama-server --jinja`) and point `QACOPILOT_LLM_BASE_URL` at `http://localhost:8080/v1`. Expect slow prompt processing; keep contexts short.

**Windows-only pieces** (Outlook COM sending, X: drive reads) cannot run on Linux. Build them behind an interface (`Mailer`: `OutlookMailer` for Windows, `FileMailer` writing `.eml` files for dev) and develop against the stub; verify the real implementation on the Windows PC later. Use synthetic documents in `data/samples/` (never real company documents).

**Workflow:** commit on branch `qa-copilot`, push, and pull on the work PC. `.env`, `infra/.env` and `infra/.langfuse/` are gitignored; recreate them per machine.

**One command on the laptop:** `./start.sh` sets up what is missing (venv and packages, Docker services, migrations, web build) and starts the API in the background (log `logs/api.log`, listens on the Docker bridge address unless `QA_HOST` is set; `QA_PORT` for the port). `./start.sh stop [--all]` and `./start.sh status`. It is idempotent, so it is also "start it again". No systemd service on purpose (personal laptop, not always on).

## Architecture

Two installable packages: `packages/qacopilot` (library) and `services/api` (FastAPI, imports the library). Settings come from `qacopilot.config.Settings`, env prefix `QACOPILOT_`, read from `.env` in the working directory (gitignored; template `.env.example`).

**LLM provider abstraction** (`qacopilot/llm/`): business logic depends on `BaseLLMProvider` (`chat`, `health`, `extract`), never on the OpenAI SDK. `OpenAICompatibleProvider` is the only implementation; it targets any OpenAI-compatible server. `thinking` is a per-request flag sent as `chat_template_kwargs.enable_thinking`, default off.

**`extract()` is deliberately defensive.** LLM servers differ in what they enforce (`response_format`, thinking flags), so `extract()` also puts the schema in the system prompt, pulls the JSON object out of fences/prose (`_extract_json`), validates with Pydantic, retries with the specific field errors, and doubles its token budget when a reply is cut off. Models answer dates as "14 March 2026" unless the schema field description says ISO `YYYY-MM-DD`; put that hint on every date field in real extraction schemas. `extract(..., thinking=True)` lets a reasoning model think first: used by the LLM judge and the classification fallback, not for reading fields.

**Design rule from the plan:** the LLM reads and drafts; code decides. Expiry queries are SQL and spec-limit checks are deterministic (reuse the toolkit's `parse_numeric_value`/`evaluate_result` logic rather than asking the model).

**Tracing:** if both `QACOPILOT_LANGFUSE_PUBLIC_KEY` and `_SECRET_KEY` are set, `_client_class` swaps in `langfuse.openai.AsyncOpenAI` (a drop-in) and sets the `LANGFUSE_*` env vars the SDK reads. Without keys it is plain `openai`; `langfuse` is the optional `tracing` extra.

**Deployment (today the whole stack runs on the Linux laptop via `./start.sh`; the split below is the production design for the Windows work PC):** the API/worker run on the Windows work machine (Outlook COM and the X: drive are Windows-only, so no Linux containers for them). The LLM runs on another machine. Postgres, Qdrant and self-hosted Langfuse run via Docker on the Linux laptop, set up by `infra/setup-laptop.sh` (calls `setup-services.sh` and `setup-langfuse.sh`; generated secrets land in gitignored `infra/.env` and `infra/.langfuse/`; Langfuse is cloned from upstream and customised only through a generated `override.yml`). These scripts use `set -euo pipefail`, so any command in them that can fail must be guarded with `|| true` (an unguarded `hostname -I` previously killed a run silently). They have not been run by Claude (no Docker on the Windows machine).

## Ingestion and retrieval (`qacopilot.ingest`, `qacopilot.retrieval`)

`extract_pages` (PyMuPDF text layer, per-page Tesseract OCR fallback) -> `classify_text` (weighted regex rules) -> `chunk_document` (strategy per `DocType`, see PLAN.md section 6) -> `QdrantStore` (dense `bge-small-en-v1.5` + BM25 sparse via fastembed, fused with RRF). Tests use `tests/fakes.py` (`FakeEmbedder`) and in-memory Qdrant, so CI needs no model download or server. Changing `embedding_model` requires re-indexing (the collection's vector size is fixed at creation).

`Retriever` = hybrid search, then `FastEmbedReranker` (cross-encoder, absolute scores), then drops hits below `rerank_min_score` (default 0.0, in the gap between out-of-scope and in-scope scores in `evals/results/rerank.json`; re-check on real documents). `rag.answer_question` yields `sources` / `token` / `no_answer` / `done` events and does not call the LLM when nothing relevant is retrieved; prompt text is versioned in `rag/prompts.py`. The API (`qa_api.main`) exposes `POST /ingest` (multipart PDF, 50 MB cap, `%PDF` check; `doc_id` = content hash so re-upload replaces) and `POST /ask` (SSE with keep-alive pings, see `qa_api/sse.py`), both behind `X-API-Key` when `QACOPILOT_API_KEY` is set. API tests use `services/api/tests/stubs.py`.

**Evals:** `evals/golden/v1.json` (18 in-scope + 3 out-of-scope questions over the synthetic corpus in `data/samples/`), scoring in `qacopilot.evaluation`. Recorded: `results/baseline.json` (hybrid only, doc hit@1 0.944) and `results/rerank.json` (with reranker, 1.0). The set is small and nearly saturated, so treat it as a regression guard; grow it in Phase 6.

## Extraction, storage and compliance (`qacopilot.extraction`, `.repositories`, `.compliance`)

`extract_document` sends the page text to `llm.extract()` with a per-type Pydantic schema (`CalibrationCert`, `CoA`, `SupplierSpec`; prompt `extract_v3` in `extraction/prompts.py`). Values are kept **as printed** (`"<10"`, `"12 months"`); decisions are made in code by `compliance.limits` (`parse_numeric_value`, `parse_limit`, `evaluate_result` -> PASS/FAIL/REVIEW; anything unreadable is REVIEW, never a guess) and `compliance.check.check_coa_against_spec` (spec limit wins, report limit is the fallback, a spec limit missing from the report is REVIEW and stops the overall PASS). These re-implement the toolkit's `parse_numeric_value`/`evaluate_result` semantics because this project may not import `gressingham_automation`.

Postgres (SQLAlchemy 2.0 async, psycopg 3, Alembic in `packages/qacopilot/migrations`): `documents`, `document_pages` (full text, so re-extraction needs no re-upload), `extractions` (JSONB, any type), `calibration_certs` (typed, for SQL). `DocumentRepository.certificates_due` considers only the **latest certificate per instrument serial** (`DISTINCT ON`), so a recalibrated probe's old due date raises no alert. `/ingest` records the document first, then indexes it; the LLM runs only on `POST /documents/{id}/extract` (10-20 s with this reasoning model). Other endpoints: `GET /documents/{id}/extraction`, `GET /certificates?expiring_within=30d`, `GET /compliance/coa-check?coa=&spec=`. DB tests use `repositories/testing.temporary_repository` (a throwaway schema in the configured database, or `QACOPILOT_TEST_DATABASE_URL`; skipped when unreachable). CI runs a Postgres service.

`evals/run_extraction.py` scores `evals/golden/extraction_v1.json` (10 documents, 60 fields) with `qacopilot.evaluation.extraction`; recorded `results/extraction_baseline.json` (v1) and `extraction_v3.json` = 60/60 (clean synthetic documents, lenient formatting comparison, so a floor check). Against real-format certificate text the LLM agrees with the toolkit's regex parser on 11/11 calibration dates, 10/11 serials and 10/11 expiries (`evals/TOOLKIT_COMPARISON.md`): field descriptions must list the label variants ("Valid To", "Next test due", ...), required strings have `min_length=1`, and house rules such as Marel's month-only expiry stay in code.

## The agent (`qacopilot.agent`, `qacopilot.mail`)

`build_graph` (LangGraph, `agent/graph.py`): `route -> answer | plan -> gather -> draft -> request_approval -> execute | rejected`. **Nothing is delivered before a person approves**: `execute` is only reachable after `request_approval`, whose `interrupt()` pauses the run (state lives in the Postgres checkpointer, so it survives restarts). The router is deterministic (`RuleRouter`: action words -> action, else question; `Router` is a protocol so an LLM router can replace it) and the tools are typed functions, not LLM-chosen: the LLM never picks an action or a recipient. For reminders, code supplies every fact (the table comes from `certificates_due`) and the LLM writes only a one-or-two sentence intro, which falls back to fixed text if it contains digits, links, or is odd (`agent/drafts.py`). Recipients come from `QACOPILOT_REMINDER_RECIPIENTS`; with none the run is `blocked`, never guessed.

Safety properties, each with a test in `tests/test_agent.py`: approving twice or at the same moment lets exactly one caller win (`AgentRepository.transition` is an atomic `UPDATE ... WHERE status=`; the loser gets HTTP 409); every email goes through the `outbox` table keyed `<run_id>-<n>`, so a retried approval or re-driven node cannot send twice (a crash between sending and recording could still resend, which is why `outlook_mode` defaults to `draft`); a failed delivery is `delivery_failed` and `POST /agent/runs/{id}/retry-delivery` re-sends only what failed; `request_approval` must have no side effects before `interrupt()` because LangGraph re-runs a node from its first line on resume.

Mail: `Mailer.deliver(message, key=...)`. `FileMailer` writes `.eml` files to `QACOPILOT_MAIL_OUTBOX_DIR` (default `outbox/`, gitignored); `OutlookMailer` (Windows COM, `QACOPILOT_MAIL_BACKEND=outlook`) saves to Drafts (`outlook_mode=draft`) or sends (`send`). Its COM session is injectable, so the logic is tested on Linux; **the real COM path has not been run and must be verified on the Windows PC**. Messages are validated (addresses, no header injection) and idempotency keys must be plain tokens (they become file names).

**Accounts (`QACOPILOT_ACCOUNTS=true`, `qacopilot.auth`, `repositories/users.py`, migration 0008).** People register on the sign-in screen with a name and a **4-digit PIN** (`POST /auth/register`, `/auth/login`, `/auth/logout`); the PIN is a salted scrypt hash and sessions are random tokens stored only as a SHA-256 digest (12 h). The token is sent in the same `X-API-Key` header, so `require_api_key` accepts either a configured API key or a live session and nothing else in the API changed. With accounts on, every request needs a sign-in even when no API key is configured. A PIN has only 10,000 values, so the protection is the **lock-out** (5 wrong PINs lock that account for 5 minutes, even for the right PIN), per-address throttles (`qa_api/throttle.py`, in memory, per process) and **keeping the app off the open internet**: LAN only. Anyone who can reach the app can register and gets full access, including approvals; there are no roles yet. **Administration.** `QACOPILOT_ADMINS="Joe Rudling, ..."` names the people who may use the **Accounts** tab (`GET /admin/users`, `POST /admin/users/{id}/pin|unlock|sign-out`, `DELETE /admin/users/{id}`; `/me` returns `admin`). Admin names are reserved on the web sign-up form so nobody can claim them: make the account in a terminal with `.venv/bin/python -m qa_api.users create "Name"` (hidden PIN prompt; also `reset-pin` and `list`, the way back in if the admin forgets their PIN). An admin cannot delete their own account, a new PIN also signs the person out and lifts a lock, and every admin action is written to `audit_log` (actor, `admin.*`, account name). Tests blank `QACOPILOT_ACCOUNTS`, `QACOPILOT_ADMINS` and `QACOPILOT_METRICS_TOKEN` in `services/api/tests/conftest.py` because `Settings()` reads the developer's `.env`.

Identity and audit: `QACOPILOT_API_KEYS="alice:key1,bob:key2"` gives each person a key, and approvals record the caller's name (the single legacy `QACOPILOT_API_KEY` is user `api`; with no keys configured everyone is `dev`). `audit_log` is append-only, enforced by a trigger in migration 0002 (UPDATE/DELETE/TRUNCATE raise; a DB owner could still drop it, so it stops accidents and app bugs, not a malicious admin). Endpoints: `POST /agent/runs`, `GET /agent/runs?status=awaiting_approval` (the approval queue), `GET /agent/runs/{id}`, `POST .../approve`, `.../reject`, `.../retry-delivery`, `GET .../audit`, `POST /feedback`. The agent starts in the API lifespan (needs `QACOPILOT_DATABASE_URL`; without it `/agent/*` returns 503).

Feedback and tracing (`qacopilot/tracing.py`): each `/ask` call gets a request id (`X-Request-Id` header; an agent run's id is its `run_id`). A context variable carries it to the LLM provider, which tags its Langfuse calls with `trace_id_for(request_id)`; `POST /feedback` stores the rating in Postgres and records a boolean `user-feedback` score on that same trace. **Set the request id in the endpoint, not inside a generator**: `stream_events` runs each step in its own task, so a value set mid-stream never reaches the LLM call (a test guards this).

Not built (by choice, noted in PLAN.md): the `extract` route (use `POST /documents/{id}/extract`) and the CoA-vs-spec check as an agent action (use `GET /compliance/coa-check`); `POST /agent/runs` runs synchronously (up to about a minute with this LLM), so the front end should show progress.

## Front end (`web/`)

React 19 + TypeScript (strict) + Vite, no UI framework. **The typed client is generated**: `web/openapi.json` (written by `services/api/export_openapi.py`) -> `openapi-typescript` -> `src/api/schema.d.ts`, used through `openapi-fetch` (`src/api/client.ts`). Both generated files are committed and CI fails if they are stale, so changing an endpoint means re-running the two generators. `/ask` is the exception: it streams SSE over POST, which neither EventSource nor OpenAPI types handle, so `src/api/sse.ts` reads it with `fetch` and mirrors the event types by hand (keep in sync with `qacopilot.rag.answer`).

Pages: **Ask** (streamed answer; `[n]` markers become links that open the cited page's text with the passage highlighted via `GET /documents/{id}/pages/{n}`, since original PDFs are not stored; thumbs up/down use the `X-Request-Id`), **Documents** (upload, list, run extraction, certificates due), **Approvals** (queue, run detail, approve/reject, audit history). Approving takes two clicks by design ("Approve..." then "Confirm and send") and the confirmation names the recipients and the signed-in user. The API key is entered on a sign-in screen and kept in `sessionStorage` only; any 401 returns to sign-in.

**Folder upload.** Documents has an **Add a folder…** button (`<input webkitdirectory>`; subfolders included): it keeps `.pdf/.jpg/.jpeg/.png`, skips the rest and says how many, uploads them one at a time through `POST /ingest`, then (box ticked by default) reads the fields of each calibration certificate, report and spec, waiting for a bundle's background job before starting the next because the server runs one extraction at a time. A Stop link ends the run after the current file. Nothing new on the server; the 50 MB limit applies per file.

One origin: in development `vite` proxies the API paths (list in `vite.config.ts`: add a path there when adding a top-level route); in production `qa_api.main` serves `web/dist` after all API routes (`mount_web`), so build with `npm run build` and no CORS is needed. TypeScript is pinned to 5.x because `openapi-typescript` does not support 7 yet. Tests (vitest + Testing Library, `src/test/mockApi.ts` stubs `fetch` by "METHOD /path") include a check that nothing is sent before the confirm click. **The UI was checked in a real browser on 2026-11-19** (Ask with a streamed cited answer, Documents with Extract, Approvals through the two-click confirm, and the LLM-unreachable error); screenshots are in `docs/screenshots/` and the README. An `/ask` failure is sent as an SSE `error` event whose data **must carry `"event": "error"`** (the client dispatches on that field; the client also falls back to the SSE event name); an unreachable LLM fails after about 20 s (connect timeout `llm_connect_timeout_s`, 1 retry) with a specific message. The reminder window is capped at 365 days and the run's message says when a longer request was shortened. A dropped connection (API restarted, network down) is turned into an ordinary 503 with `NETWORK_MESSAGE` by an `openapi-fetch` `onError` middleware in `src/api/client.ts`, so every page's existing error branch shows it (before, an unhandled rejection left buttons stuck on "Working…"); only `TypeError` is converted, so aborts and real bugs still throw, and the streaming `/ask` client maps the same error through `errorMessage`.

**Due-date questions skip search (`qacopilot.rag.lookup`).** `/ask` first asks `answer_with_lookup`: if the question is about when calibration certificates are due (`is_due_question`: a due/expiry word plus a calibration word or a serial-like token), it is answered **deterministically from the certificates table** (`DocumentRepository.latest_certificates`: latest certificate per serial; earlier ones, de-duplicated, are attached as `older` and named "superseded"), with `done.via == "certificates"`, one citation per instrument, and no LLM call. Instruments are chosen by serial named in the question, then by instrument words in the description ("probe", "x-ray"; every match is listed, never one picked), then by a list question ("which certificates expire next month", window from `qacopilot.timewindow`). Anything it cannot place (BRC/audit/spec words, an instrument not in the table, no certificates extracted) returns None and falls back to search; a database error also falls back. The answer discloses calibration documents not yet extracted (`unextracted_calibration_documents`). Search alone had cited a superseded certificate with confidence (the q22 failure). `get_repository_or_none` keeps Ask working without a database; tests that override `get_repository` must override it too.

**Choosing the spec for a CoA (`qacopilot.compliance.pairing` and `.service`).** `run_coa_check(source, coa_id, spec_id=None)` is the one place the check is run; `GET /compliance/coa-check` (spec now optional) and the Ask path (`rag/coa_lookup.py`, `done.via == "coa_check"`, triggered by a judging word plus a batch reference) both use it. Without `spec_id`, `pair_spec` matches by product (every word of the report's product, after trimming an OCR run-on such as "... Batch: B2701-02", must be in the spec's; Jaccard breaks ties), groups candidates by supplier + product + code, and returns `paired`, `ambiguous` (HTTP 409 listing the candidates; different suppliers or products that fit equally well are never guessed) or `no_spec` (404). Within one spec the revision in force on the report date is used (revision number and effective date are **read from the spec's own page text in code**, not the schema, so the extraction prompt and its recorded hash are unchanged); a report with no date uses the newest revision and says so. A revision whose text says its micro limits are "unchanged" and lists none borrows the earlier revision's limits (`limits_from`), and says so; without that statement nothing is borrowed. OCR'd inputs still cap a pass at review.

**Review of unverified readings (poor scans).** A `calibration_certs` row has `needs_review` (+ `review_reason`, `verified_by/at`, migration 0007) and an append-only `certificate_reviews` table (who, action `confirm`/`correct`, values before and after, note). `save_extraction` sets `needs_review` from `DocumentRepository._review_state`: pages with OCR confidence under `POOR_OCR_CONFIDENCE`, `certificate_warnings` (implausible dates), and **`ungrounded_fields`** (`extraction/checks.py`): the serial and each date must literally appear in the page text, because OCR confidence missed a degraded scan from which the model invented a serial and a date. Re-extraction keeps a person's confirmation only if the new reading has the same serial and dates; otherwise it goes back to the queue saying it differs from what the person confirmed (a re-run never silently erases human work). `review_certificate` validates corrections through `CalibrationCert` (only the five `CORRECTABLE` fields), updates the typed row **and** the stored extraction, and records the change. API: `GET /certificates/review`, `POST /documents/{id}/certificates/{start_page}/review` (body `corrections` null = confirm as is), `GET .../reviews` (history); the reviewer is the API-key user. `CertificateStatus` and `InstrumentCertificate` carry `unverified`: due-date answers append "UNVERIFIED", reminder emails mark the row and add a fixed caution sentence (code, not LLM). UI: `components/ReviewQueue.tsx` on the Documents page.

**Questions that combine conditions (`rag/specquery.py`).** One handler per question shape kept dropping whatever it did not know ("how many Tesco duck breast specs" counted every Tesco spec; "specs with no allergens" counted all 550; "which whole duck specs use X" ignored "whole duck"; a number made up from five passages for "Tesco specs that use Reflex"). The query layer reads a question once into a `SpecQuery` (intent: count, list, distinct, rank, compare, common, packaging, oldest, newest, most_revised, plus `content` and `unsupported`; a `SpecFilter` of product phrase, customer, frozen/fresh, allergens yes/no, version, year, and packaging conditions `PackCond` with code/supplier/type/section and `negate`), **the model only translates** (`llm.extract`, prompt in the module) and **code decides**: `validate` checks every name against the data (customers, suppliers, product words, codes; typos are corrected and said: "Lidll read as Lidl"), `_ground` drops anything the model invented that is not in the question (it once copied "whole duck" from a prompt example), `_enrich` adds what the question names but the model left out (a supplier, customer, code, packaging type, primary/secondary, frozen/fresh), unknown capitalised names are reported, and one SQL query built from validated pieces answers. **Every answer starts with "Understood as: ..."** so a misreading shows. `needs_engine` routes only what a single-shape handler would answer in part (two or more conditions, negation, compare, "both X and Y", ranking or listing specs, dates, distinct customers, a typo word); one-condition questions stay with `packaging.py` / `factspec_lookup.py`, whose output the older probe suites check. `content` returns None (search reads what a spec says) and `unsupported` says why the tables cannot answer ("which packaging codes are not used by any spec"). A count or list over the specs that nothing could read is **never left to search** (`looks_like_aggregate`, `GUARD_MESSAGE`), and a bare "help", "specs", a customer or a product word gets a menu or a short profile (`answer_vague`). `answer_with_lookup(question, source, fallback, llm)` needs the model for this layer. Packaging rows are matched by supplier word-prefix ("Reflex" includes "Reflex Labels"), a packaging type phrase by ordered words ("gas flush bag"), a one-word type by synonyms (`KIND_WORDS`). "Current" specs, the phrase rule and customer rule are unchanged (see below). Probe: `evals/chat_probe.py --suite hard` (31 labelled questions, expected answers from independent SQL, run it 2-3 times: the model reads slightly differently each time) plus the 100-question `groups` and 142-question `general` suites; all pass. The 70-question review that found these failures was manual (24 fine, 18 a condition silently ignored, 12 refused though answerable, 6 incomplete lists, 1 invented number).

**What a spec says, read in code (`ingest/factspec.py`, migration 0011).** Besides the header and packaging, `parse_fact_spec` reads the rest of the template into `fact_specs` columns and `spec_versions`: weight and weight type, the storage line and its temperature range (`temp_min_c`/`temp_max_c`; "0°C to 3°C", "0°-3°C", "-18oC", "frozen - 18°C" and "frozen-18°C" are all handled, a hyphen before a number is a minus, and a "frozen" spec is never above zero), max life and the minimum life into the depot (text plus days; a month is 30 days; `life_basis` kill/pack; a blank or "see shelf-life table" figure stays NULL with `life_notes`), the pallet table (labels vary, so it reads from the labels up to "Type of Pallet" and then the same number of values; "N/A" is NULL, never 0), metal detection stick sizes in-line and X-ray in mm (`2x 6mm` / `N/A` are kept as text), pack and case tare in grams, the ingredient table, the process steps, and the **version history** (version or "Creation", person responsible, page, amends, date; two-digit years and `21.12.15` dates; a row must look like one, so the text after the table is never read as history). Coverage on the 550 real specs is 98-100% for storage, weight, steps and history and 79-95% for the others; the rest are bulk (dolav) specs that print N/A. **A "WEIGHT:" or "TEMP:" label needs its colon** (the packaging table also has a column called Weight). `DocumentRepository.rebuild_fact_specs()` re-reads every spec from the stored text: run it after improving the parser. Single-spec questions ("what is the max life for 4056877", "what temperature should it be kept at", pallet, metal detection, weight, ingredients, process steps, "who last updated it") are answered from these columns in `factspec_lookup._detail_answer`; "who approved" says plainly that a spec records who changed it, not an approver. The query layer filters and orders by them: `SpecFilter.numeric` (a whitelist of fields and `gt/gte/lt/lte/eq`), `storage_c` (the spec's range includes the value), `person` with role any/last/created, `SpecQuery.order_by` ("the longest max life"), rank by `person`. **The model's numbers and flags are not trusted**: a number must be in the question (a month or kilogram may have been converted), frozen/fresh, allergens, a year or a version must be named in it, a superlative with a field name ("shortest max life") becomes ordering and never a filter, and product words the model dropped are restored (never a number or a field phrase). These came from real failures: "how many turkey specs are for Wholesale" read as "customer Wholesale, frozen" 12 times in 12, "shortest max life" as "at most 0 days", and a product called "100". The probe's `fields` cases recompute their expected answers from the raw page text with a separate regex (it found the "-18" parsing bug, 92 specs against 98).

**Name aliases (`name_aliases`, migration 0012, `qacopilot/aliases.py`, `python -m qa_api.aliases`).** One customer is spelt several ways ("Sainsbury", "Sainsbury's", "Sainsbury’s", "TESCO", "Tesco Certification/Retail"), which split counts and lists. `suggest` groups spellings and marks them `safe` (case, apostrophes, punctuation, plural) or `check` (a Certification/Retail tag, Foods/Ltd, a typo); the canonical name is the most used spelling that is not a tagged variant; a string joining two names ("Booker/Brakes") is never suggested. **Nothing is applied until a person approves rows** (`suggest --out FILE`, put `yes` in the approve column, `apply FILE`; also `list`, `add`, `remove`). An alias is applied in SQL (`DocumentRepository.canon(kind, column)`, kinds customer/supplier/person) wherever a name is filtered, counted or grouped, and in reading a question (a typed spelling resolves to the canonical name). The file holds customer names and belongs in the gitignored `logs/`. **In force now: 71 aliases** (every row of the reviewed `logs/aliases_proposed.csv`, approved by the owner on 2026-11-21, plus "Peter" -> "Peter Bringlesnap" added earlier; reverse one with `python -m qa_api.aliases remove <kind> "<name>"`). Customers went from 120 to 87, packaging suppliers from 118 to 88, people from 25 to 21 (Sainsbury's 8 -> 41, Tesco 32 -> 38, Morrisons 25 -> 33). Supplier counts and a typed supplier spelling use the aliases too. The probe applies aliases to its expected-answer SQL in one place (`with_aliases` in `evals/chat_probe.py`). **Names to check (Admin page, `qacopilot/names.py`, migration 0013 `name_decisions`):** `GET /admin/names` lists names that need a person, each with a recommendation ("probably an alias of X" or "probably a new name"), the reason and the closest names; `POST /admin/names/alias` (name, canonical; canonical must already be a name in the specs) and `POST /admin/names/separate` (remembered, never suggested again) settle one and are audited (`admin.alias`, `admin.name_separate`). Sources: `aliases.suggest`/`suggest_people`, plus names used by 2 specs or fewer that resemble a more common one (a rare name that resembles nothing is not listed; customer names that join two ("Booker/Brakes") and alias targets are skipped). A change clears the vocabulary cache so questions see it at once. A spelling people type finds the customer in every handler (`DocumentRepository.resolve_name`, and `_names_in` ignores case, apostrophes and a plural s), and a customer, supplier or person word is never kept as a product word (`_strip_named_from_product`).

**Follow-up questions (`specquery.merge_with_context`, `AskRequest.context`).** After a list or count the chat remembers the answer's `export.query` and sends it as `context` with the next question (`web/src/pages/Chat.tsx`; a **New topic** button clears it; any answer without an export, such as a document answer, ends the thread). `is_follow_up` (starts like a refinement: "from Tesco", "only frozen", "and Lidl", "what about", "give me all"; or points back: "of those", "them") with a context makes `answer_from_specquery` read the question without its cue words, validate it alone (so grounding still drops anything the question does not say), then lay its conditions over the previous query: a condition stated again replaces the old one, the rest carries over, packaging and number conditions add up. A question that names a product of its own is not a refinement. The kind of answer follows the words ("how many" counts, "give me/show/list/which" lists, else the last kind stays); "show me all of them" with no new condition lists the last query. The answer says "continuing from your last question: ...". The older single-condition handlers (`factspec_lookup` counts, packaging "which specs use code X") now also return an `export` query so they can be refined and downloaded. The server keeps no conversation: the browser holds it. Probe: ask the questions in sequence through `POST /ask` passing the previous `done.export.query` as `context`.

**Download of every row (`POST /export/specs`).** A list answer shows 25 specs; any count, list, distinct, rank, packaging, oldest, newest or most-revised answer from the query layer carries `done.export = {query, count}`, and the chat shows **Download all N specs (CSV)**. The browser sends the validated query back; `export_specs` validates it again exactly like one read from a question (names against the data, every value a SQL parameter), returns up to 5000 current specs (NAV code, product, customer, type, status, version, version date, allergens, file name) as UTF-8 CSV with a byte-order mark so Excel opens it, and a cell that would run as a formula (`=`, `+`, `-`, `@`) is written as plain text. A comparison has no list and is refused (422). It needs a sign-in like every other endpoint.

**Fact Specs and packaging (`ingest/factspec.py`, `rag/packaging.py`, migration 0010).** Gressingham's own product specs (`DocType.FACT_SPEC`, classified by the "Fact Spec" filename and the `NAV CODE` / `EXCHEQUER` + `PLU` + `VERSION` + `SITE` header labels) are read **in code, with no LLM**, when they are saved: `parse_fact_spec` fills `fact_specs` (NAV code, PLU, version and date, product, customer, status, ...) and `spec_packaging` (one row per coded packaging line: section, code `70/79xxxxx`, qty, description, supplier, dimension, weight, page, and the raw `cells`). The PDF text is one table cell per line, so a row's code and quantity are reliable and the other columns are a best reading (a code the PDF wrapped over two lines is rejoined; an uncoded crate row is skipped; the "Pack Tare / OCM / Product weight" totals end the table). A blank description or supplier borrows the most common one for that code. "Current" means the **latest version of each NAV code**, so an old revision's packaging is not counted. Ask answers packaging questions from the table (`via == "packaging"`, no LLM): the most used codes (`top N`, `primary`/`secondary`), which specs use a code, and what packaging one NAV code uses; anything else falls back to search. Search alone cannot count across specs (it reads five passages). `DocumentRepository.rebuild_fact_specs()` re-reads every Fact Spec's tables from the stored text after the parser improves. Fact Specs are not LLM-extracted (no Extract button). 2 of the 552 uploaded specs use an older inline header ("Exchequer:  4054554") and stay `supplier_spec`.

**Fact Spec questions and the chat probe (`rag/factspec_lookup.py`, `evals/chat_probe.py`).** Besides packaging, Ask answers from the `fact_specs` header table (`via == "fact_spec"`): one spec's customer, version, status, PLU, season, brand, type, allergens, certification or product name, a "tell me about spec NNNNNNN" card, and counts ("how many specs are frozen / for Tesco / declare allergens", "which customers have the most specs"). Customer matching is case-insensitive ("Tesco" and "TESCO" are one customer). A question that names one spec (a NAV code, or a product name that is wholly in the question; `match_specs`) is **searched within that spec only** (`doc_id` filter) and its NAV code is swapped for the product name first, because a question made mostly of a code scores below `rerank_min_score` and retrieves nothing. When two or more current specs share the product name (the same product for two customers) search stays open and the answer ends with a note listing their NAV codes instead of silently picking one. `evals/chat_probe.py` builds 100 questions at run time from the live database (so the real documents stay out of git and every expected answer is computed from the same tables), asks them through `POST /ask` with `PROBE_TOKEN`, and scores them: packaging ranking/code/per-spec, header fields, counts, content questions (must cite the right spec) and out-of-scope refusals. It writes answers (company data) to the gitignored `logs/`. 99/100 on the first full pass after the table lookups were added; now 118/118 including product-group ("packaging codes used for whole duck", from `packaging_for_products`) and typo (`fix_typos`: "packging", "pakaging") questions. A question that is not recognised as a packaging question falls to search, which cannot list codes and once answered something unrelated, so misspellings of "packaging" are corrected first. Known data quirk: a few packaging rows have a stray weight fragment in the supplier column ("2.6"), because the PDF text splits cells unevenly.

**Reports and specs are reviewed too (`extractions.needs_review`, migration 0009).** `save_extraction` runs `coa_problems` / `spec_problems` (`extraction/checks.py`) on a CoA or spec: a test name printed on the page (TVC, Enterobacteriaceae, Salmonella, Listeria, E. coli, ...) with no result/limit read for it, a batch, result or product that is not in the page text, a printed date with no report date read, a mentioned shelf life or storage that was left empty, poor-scan pages. Checked on the synthetic reports and specs with the real model: 0 of 10 clean documents flagged (a report that prints no date at all is deliberately **not** flagged; only "a date is printed but none was read"). `GET /review/documents` lists them; `POST /documents/{id}/extractions/{start_page}/review` confirms or corrects the scalar fields only (`CORRECTABLE_DOC`; the list of results or limits is not editable, a missing row means re-running extraction); audit rows go in `certificate_reviews`. Re-extraction keeps a confirmation only if the reading is identical. `run_coa_check` caps the verdict at review and warns while either document is unconfirmed (so tests that feed partial extractions must confirm them first, see `_confirm_flagged`). A missing next-due date on a certificate was already a review reason (`certificate_warnings`).

**Classifier margin (`ingest/classifier.py`, `llm_classifier.needs_second_opinion`).** `Classification` carries `margin` (winner minus runner-up score) and `runner_up`. Confidence alone could not see a near tie (a dead tie settled by the title bonus still reported 1.0), so the LLM is also asked when `margin < DEFAULT_MIN_MARGIN` (3.0, one strong phrase); a disagreement is flagged, the rules' type is kept. On the real set this asks about 9 of 22 documents (the fragile ones among them). The LLM's answers vary run to run (hybrid 0.955 to 1.00 over three runs of the same 22 documents), so a single run is not a trustworthy number; `evals/run_classification.py` records `fragile_but_correct` (right answers by a margin under 3), the figure to watch as the rules grow. The rules score of 1.0 on the real set is tuned, not an estimate.

**Monitoring (`qa_api/metrics.py`, `qacopilot/metrics.py`, `infra/monitoring/`).** Prometheus + Grafana, set up by `infra/setup-monitoring.sh <api-host:port>` (Grafana :3001, Prometheus 127.0.0.1:9092; 3000, 9090 and 9091 are Langfuse/MinIO). `prometheus-client` is a hard dependency of `services/api` and an optional `metrics` extra of the library, whose `qacopilot.metrics` is a no-op without it (`llm_call("chat")` times and counts each LLM call: ok/error/unreachable/cancelled). `GET /metrics` (not in OpenAPI) needs `Authorization: Bearer $QACOPILOT_METRICS_TOKEN`, else the API key. A pure-ASGI `MetricsMiddleware` labels requests by **route template** (`scope["route"].path`; unknown paths are `unmatched`, the static mount `static`), never the concrete path, so series do not grow per document id; keep every label to a small fixed set (never a question, filename or user). Ask is wrapped by `measured_ask` (path = `DoneEvent.via`, outcome answered/refused/error). Gauges that need the database (review queue, overdue, approvals waiting and oldest age) and the Postgres/Qdrant/LLM `qacopilot_dependency_up` probes are refreshed by a background task every 30 s started in `lifespan` (a scrape must never wait on a down dependency; probes time out at 8 s). `qacopilot_metrics_refreshed_timestamp_seconds` only advances when the database read succeeds, which is what the "queue data stale" alert watches. The dashboard JSON is generated by `infra/monitoring/make_dashboard.py` (do not hand-edit the JSON); alert rules are `prometheus/alerts.yml` (check with `promtool check rules`); the generated `prometheus.yml` and `metrics_token` are gitignored. **Alerts go to ntfy:** `infra/monitoring/alertmanager` (Alertmanager on the host network, listening on the Docker bridge address `172.17.0.1:9093`) posts each alert to `$NTFY_URL/$NTFY_TOPIC` (default `http://127.0.0.1:8091/kvack-alerts`, the ntfy that another project runs on this laptop) with a message template, so no relay is needed; resolved alerts are sent too, a lasting problem repeats every 4 h. Open that address in a browser or subscribe to the topic in the ntfy app (a phone needs ntfy reachable from it, which it is not by default: it only listens on 127.0.0.1). `alertmanager.yml` is generated from the template by `setup-monitoring.sh` and gitignored; re-run the script with `NTFY_URL=... NTFY_TOPIC=...` to change where alerts go.

## Evals and CI gates (`evals/`, `qacopilot.evaluation`)

Golden sets: `golden/v3.json` (43 questions: v2 plus `due_date` and `coa_check` questions and two more refusals; items can carry `via`, the path that must answer them, so a question that should come from the certificates table or the spec check fails if search answers it; `run_answers.py` seeds a throwaway Postgres schema from the golden extractions via `evals/common.seed_repository`, so it needs a database) is the answer set; `golden/v2.json` (35 questions, still the retrieval set: 29 answerable + 6 out of scope, categories lookup / near_duplicate / table / clause / scanned / adversarial / out_of_scope; each lists expected `(doc, page)` pairs, `answer_contains`, `answer_excludes`), `golden/extraction_v2.json` (18 documents, 108 fields), `golden/compliance_v1.json` (expected CoA-vs-spec verdicts). The corpus is `data/samples` (27 synthetic PDFs, regenerated by `make_samples.py`, which never overwrites existing files without `--force`). `v1` files are kept for history.

Four layers, cheapest first: **retrieval** (`run_retrieval.py`: doc/page hit@k, MRR, no LLM), **answers** (`run_answers.py`: real LLM; deterministic scoring in `evaluation/answers.py`: required and forbidden phrases, correct refusal, citation present and correct; errors never count as correct refusals), **extraction** (`run_extraction.py`), **judge** (`run_judge.py`: faithfulness and relevance by the same model, so only a trend indicator; it saw q05 as unfaithful because the revision-1 document never says "revision 1"). Runners refuse to record a result if most calls errored (a wrong working directory once produced all-404 results). **Always run them from `qa-copilot/`** so `.env` is found.

Recorded results live in `evals/results` and are committed: `rerank_v2` (retrieval), `baseline_v2` (hybrid only), `answers_v3` (the gate; `answers_v2` is kept for history), `answers_v2_per_hit_cutoff` (before the cut-off fix), `extraction_v2`, `judge_v3`. `thresholds.json` holds the floors and `prompt_hashes.json` the fingerprint of each prompt version. `check_recorded.py` (also `tests/test_recorded_evals.py`) re-scores the recorded files, checks floors, checks that recorded prompt versions match the code, and fails if a prompt or extraction schema text changed without a version bump. After a deliberate improvement: run the live evals, then `check_recorded.py --write`, and review the diff.

CI: `ci.yml` (GitHub-hosted: lint, mypy, tests with a Postgres service, `export_openapi --check`, the offline gate, and the `web` job) and `evals-llm.yml` (self-hosted runner `[self-hosted, linux, llm]` on the Linux machine; push to main and manual dispatch only, never `pull_request`, because it can reach the LLM; secrets `QACOPILOT_LLM_*` and `QACOPILOT_LANGFUSE_*`). Live runs write `*_ci.json` (gitignored) and compare with the recorded baselines using tolerances. Scores per release go to Langfuse as `eval-<release>` scores (`evaluation/report.py`).

Findings worth remembering: the relevance cut-off (`rerank_min_score`) must look at the **best hit only** (per-chunk filtering dropped the "Limits" section that held the answer); on-topic-but-missing questions score high on the reranker so only the LLM's refusal catches them; OCR can misread digits, so compliance results built on OCR'd pages are capped at `review` (`cap_for_unverified_source`, `ocr_pages` on extractions); rotated scans were unreadable until `ingest/pdf.py` started using Tesseract's orientation detection.

## Real-document findings (`trainingData/`, gitignored)

`trainingData/Training Data/<1-7 type folders>` holds 22 real public documents (calibration certificates incl. scans and a phone photo, CoAs, specs, customer manuals, HACCP, audit certificates, odd ones). It is **never committed** (`.gitignore`); the folder number is the ground-truth type. First pass (metadata only, `scratchpad/survey.py`) found, and these fixes were made, each with a regression test in `tests/test_real_world_layouts.py` using invented text:

- Huge image (211 megapixel phone photo) crashed OCR with a decompression-bomb error: pages are now rendered at most `MAX_OCR_SIDE_PX` (4500) on the longest side; the cap beats any DPI floor.
- OCR was slow (4.7 s/page): pages are OCR'd in parallel (`OCR_WORKERS`=4) **with `OMP_THREAD_LIMIT=1`**; without that, 4 workers were slower than 1 because Tesseract already uses every core.
- JPEG/PNG uploads are accepted (`sniff_kind` judges by content, not file name).
- Classifier: reads only the first 4000 characters (a 100-page manual mentions every topic); needs a score of 3 (one strong phrase or three weak signals); a strong phrase in the title (first three short, non-numbered lines) outranks body text; learned "test certificate", "specification data sheet", "supplier technical manual". 20/22 correct on the folder labels, from 16/21.
- Chunking: unnumbered ALL-CAPS "headings" with under 40 characters of text after them (table cells like PLU, NAV CODE) stay as text. A 6-page table had become 1306 chunks, now 41.

**Bundles (built).** Most real calibration PDFs hold many certificates (counts on the real files: 1, 1, 9, 19 and 29 certificates). `ingest/bundles.py` (`split_certificates`) splits a calibration document into segments: a different serial or certificate number starts a new certificate, the same one continues it, a short page with nothing identifying it (repeated header, signature page, blank) attaches to the one before, and **a full-length certificate-like page that cannot be tied to the previous one starts a new certificate**. That last rule is deliberate: real bundles print identifiers in forms the regexes cannot read (on a 30-page file only 5 pages yielded a serial), and gluing two certificates together loses one *silently* while over-splitting fails *visibly* (one certificate "could not be read"). `extraction/runner.py` (`run_extraction`) extracts each segment (one LLM call each, 20-100 s), saves each as it finishes (`extractions` and `calibration_certs` are keyed `(doc_id, start_page)`, migration 0004), records progress in `extraction_jobs`, keeps going when one certificate fails, and prunes rows for certificates a re-run no longer finds. `certificates_due` takes the latest certificate per serial across all of them. `POST /documents/{id}/extract` answers 200 at once for a single certificate and **202 + a background job for a bundle** (one extraction at a time, per event loop; a 409 if one is already running; `fail_stale_jobs()` at startup marks a job from a dead process failed); poll `GET /documents/{id}/extraction` (`status`, `total`, `done`, `failed`, `segments[]` each with plausibility `warnings` from `extraction/checks.py`). The UI shows progress, polls while a job runs, tabulates certificates and says how many could not be read. `evals/run_real_extraction.py` runs this on the real files and prints aggregates only.

**LLM classifier fallback (built).** `ingest/llm_classifier.py`: rules first; the LLM is asked only when the rules say `other` or are under 0.7 confidence (`QACOPILOT_LLM_CLASSIFY`, default on). Policy: rules found nothing -> the LLM's answer is used (`classified_by = "llm"`); rules named a type but unconfidently and the LLM disagrees -> **the rules' type is kept** and the LLM's is stored as `alternative_type` so the UI shows a "check" badge (a keyword match is never silently overruled); a failed call -> rules. A person's choice (`doc_type` on `/ingest`, or `POST /documents/{id}/reclassify`, which re-chunks from the stored page text and drops the old extraction) is `classified_by = "user"` and clears the flag. Measured (`evals/run_classification.py`, results committed with anonymous ids for the real set): synthetic 26 docs, rules/LLM/hybrid all 1.00; real 22 docs, rules 1.00, LLM alone 0.91, hybrid 1.00 with the LLM asked on 7 and 1 flagged (SOP vs HACCP for a CCP summary, a judgement call). **The real-set rules score is not a generalisation estimate: the rules were tuned on those documents** (before tuning they got 16 of 21; the LLM got 20 of 22). `evals/golden/classification_v1.json` and `trainingData/labels.json` (gitignored) hold the labels.

## Model, reasoning and what it costs (measured 2026-11-18)

Model now: Darkstar Nemotron 3.5 Lightning 30B-A3B, **IQ4_XS** quantization (earlier runs used Q8_0), reasoning off. The eval result files record the model name, so the quantization travels with the numbers. Effect of the move to this setup, same documents: **speed** went from 15-140 s to about 1.5 s per extraction and 40 s for the whole 29-certificate real bundle (was over an hour); **answers** correct 1.00 -> 0.966 (only the stale-certificate question q22 fails), citations 1.00, refusals 6/6; **extraction** accuracy 0.981 -> 0.95-0.96 across repeated runs (0.88 before the text fallback below; the model, answering directly, skips optional fields it used to fill, and the same document can differ between runs); **judge** faithfulness 0.966 -> 0.931. `QACOPILOT_EXTRACTION_THINKING=true` bought 0.926 against 0.88 for 11x the time (346 s vs 30 s for 18 documents) measured *before* the fallback; with the fallback the fast path is already at 0.95, so it is off by default. `results/extraction_v2_thinking_on.json` is that earlier comparison. Floors in `evals/thresholds.json` were lowered to these values deliberately (answer_correct, citation_correct, extraction accuracy, judge faithfulness); older results are kept as `*_thinking.json`.

Without reasoning the model gives bare, uncited answers, so `answer_v2` has a worked example and repeats the citation rule at the end of the user message, and **`answer_question` treats a reply with no valid `[n]` as not answered**: either a refusal in the model's own words ("not provided in the given sources", matched by `_REFUSAL`, reason `not_in_documents`) or an uncited claim (reason `uncited`). `evaluation/answers._norm` ignores the degree sign. Real certificates: on the two good scans (OCR confidence about 89) 28 of 28 certificates have a distinct serial, both dates and a plausible interval; on the poor 30-page scan (confidence 61-69, and no preprocessing helped) the model returns dates, but they cannot be verified, so per-page OCR confidence is stored (`document_pages.ocr_confidence`, migration 0006), documents show a "poor scan" badge (`poor_ocr_pages`, below `POOR_OCR_CONFIDENCE` = 75) and the extraction view warns.

**Text fallback under the model (`extraction/service._fill_from_text`).** After the model answers, code fills a field the model left empty only if the document prints it with a clear label: a `SupplierSpec.supplier` or `CoA.product` from a `Supplier:` / `Product:` header line (`ingest.chunking.header_fields`, the same reader the chunker uses for metadata), and a `CalibrationCert.next_due` from a label such as "Next calibration due", "Valid To" or "Suggested date for recalibration" (`extraction/dates.py`: ISO, day-first numeric, and "2 April 2027" forms; impossible dates and anything within 40 characters of nothing are ignored; a date not after the calibration date is treated as a misread). It never overwrites what the model found. The next-due case matters most: without reasoning the model dropped a plainly printed next-due date in 2 of 3 runs on one certificate, and a missing one hides the instrument from expiry reminders. Supplier and product are not used in any decision today (the CoA check takes explicit document ids), but pairing a CoA to its spec automatically would need them.

## Gotchas
- **Route order:** `mount_web(app, ...)` must stay the LAST statement of `qa_api/main.py`. A mount at "/" answers every path, so a route registered after it returns 405. It only bites where `web/dist` exists, so `tests/test_route_order.py` checks the source order.
- **Circular imports:** `qacopilot.repositories` imports `extraction.schemas`, so `extraction/runner.py` imports `DocumentRepository` under `TYPE_CHECKING` only. Test runs hide this (fixed import order); `tests/test_imports.py` imports each module first in a fresh interpreter.
- `rglob` treats `[` in a file name as a pattern (a real file was named `...[1]...`); look files up by exact name.

- Always pass `--config-file packages/qacopilot/pyproject.toml` to mypy. Run from `qa-copilot/` without it, mypy walks up to the toolkit's `pyproject.toml` (Python 3.10, non-strict) and silently skips the strict checks.
- OCR needs the system `tesseract` binary (`apt install tesseract-ocr`); `data/samples/make_samples.py` regenerates the synthetic PDFs (the scanned ones are image-only, kept small with grayscale JPEG).

- The installed `openai` SDK (3.x) bundles its own httpx fork (`httpx2`), so `OpenAICompatibleProvider(http_client=...)` is typed `Any`; tests inject `httpx.AsyncClient(transport=httpx.MockTransport(...))`, which works at runtime.
- Never set `LANGSMITH_*` / `LANGCHAIN_*` tracing variables: `langsmith` (a LangGraph dependency) would send traces to LangChain's cloud, which breaks "nothing leaves the site". Langfuse is the only tracing.
- `Settings()` reads the developer's `.env` (real Langfuse keys) even under pytest; both `tests/conftest.py` files blank the Langfuse keys so tests never export spans or scores to a real Langfuse.
- The Postgres checkpointer wants a plain `postgresql://` URL, not SQLAlchemy's `postgresql+psycopg://`; the API lifespan converts it. Live smoke tests should use a scratch schema (`options=-csearch_path=...` in the URL), because `audit_log` rows can never be deleted.
- `pytest-asyncio` runs in `asyncio_mode = "auto"`, so async tests need no decorator.
- Windows checkout converts line endings; `.gitattributes` forces `*.sh` to LF and the scripts are committed with the executable bit.
- The LLM is reached over HTTPS on a public hostname with an API key (checked 2026-11-18: the configured base URL uses `https`). Re-check the scheme in `.env` before sending real documents; a plain `http://` URL must not carry them.
- **Switching reasoning off is server-specific, so the provider sends `enable_thinking` BOTH at the top level and nested in `chat_template_kwargs`** (`_thinking_body`). Measured: the old proxy honoured only the top-level form; the current llama.cpp server honours only the nested form. Sending one form to the wrong server costs 10x the tokens and minutes per extraction, with no error. `evals/probe.py` tells the two apart; re-run it when the LLM host changes. Reasoning tokens count against `max_tokens`; `extract()` starts at 8192 and doubles to 16384 on a truncated reply, and `llm_timeout_s` is 300.
